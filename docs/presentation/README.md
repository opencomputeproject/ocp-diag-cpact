## 1. The problem statement

Server CPUs are bought from multiple suppliers, but **accessibility is not
standardised**. Three concrete symptoms:

- **Interface divergence.** One supplier exposes a debug dump over an in-band host
  command, another over a Redfish endpoint, another only through a BMC-side utility.
  Telemetry counter names, register maps and log formats differ the same way. Nothing
  written for supplier A transfers to supplier B.
- **Per-vendor, per-generation toil.** Because nothing transfers, the operator writes
  and maintains a bespoke qualification script set for every supplier, and rewrites a
  large part of it at every CPU generation. The cost of qualification scales with the
  number of suppliers, which is precisely the opposite of what a multi-sourcing
  strategy is supposed to achieve.
- **Assertion instead of proof.** Accessibility requirements live in a specification
  document. A supplier confirms compliance in a spreadsheet. Nobody executes anything
  against real silicon until far later.

The consequence is a **late-discovery failure mode**. The gap between "the document said
this CPU is debuggable" and "this CPU cannot actually be debugged in place" is found at
fleet scale, usually mid-incident. At that point the options are bad: slow manual triage,
draining and returning nodes, or leaving capacity stranded. And throughout, there is no
objective, comparable measure of how accessible one supplier's part is versus another's.

**In one sentence:** accessibility is a requirement everyone agrees on, that nobody can
currently measure, prove, or compare.

## 2. Why we built CPACT

CPACT exists to convert that unmeasurable requirement into something executable.

- **Make the specification executable.** Requirements are expressed as versioned YAML
  scenario recipes validated against a JSON Schema. The requirement and the test that
  proves it stop being two different documents maintained by two different teams.
- **Scope it to what decides serviceability.** The domains covered are the ones that
  determine whether a node can be kept alive in production: **Debug**, **Telemetry**,
  **impact-less firmware update**, and **RAS**. These are the capabilities an operator
  actually reaches for during an incident.
- **Move the check left.** A supplier can run CPACT against their own silicon during
  bring-up and see exactly where they fail, long before parts ship. Compliance becomes
  something you can self-certify against, not something you discover you failed.
- **One contract, not N.** Under the Open Compute Project, CPACT is a single
  vendor-neutral suite. Without it, every operator–supplier pair negotiates its own
  bilateral accessibility agreement, and none of them are comparable.
- **Same recipes, every access path.** A scenario runs locally, over in-band SSH, over
  out-of-band Redfish/BMC, or through an SSH tunnel when the target sits behind a rack
  manager. What the lab validates is what the fleet will actually be able to do.

**What CPACT deliberately is not:** it is not a performance benchmark, and it is not a
replacement for vendor-specific diagnostics. It measures *accessibility* — whether the
interfaces an operator depends on exist and behave as specified.

## 3. What it does, and what you gain

| Capability | What it means in practice | Why it matters |
| --- | --- | --- |
| **YAML scenario recipes** | Scenarios are declarative YAML, grouped by domain, tag, group and ID, with multi-step sequencing and explicit expectations. | Compliance becomes code: reviewable in a pull request, diffable across revisions, versioned with the spec it encodes. |
| **Four connectivity paths** | Local, in-band SSH, out-of-band Redfish/BMC, and SSH tunnel — auto-discovered, health-checked and cached. | The suite exercises the box the same way the fleet reaches it, including the awkward paths that only exist in production topologies. |
| **Draft-7 schema validation** | Each recipe declares a `schema_version`; validation resolves the matching schema under `spec/schema/` and also validates any referenced map file. | Recipes stay portable as the specification evolves (0.7 → 0.8). Breaking spec changes are caught at validation time, not at 3 a.m. |
| **Weighted scoring** | Schema, map and execution outcomes are scored and normalised, with profile bonuses and parent/child roll-up for nested recipes. | You get a *comparable number* rather than a bare pass/fail — enough resolution to rank suppliers and track a part improving release over release. |
| **Logs, reports, evidence** | CPACT logs, workload logs and score output are written per run. | An auditable evidence trail. A compliance claim can be re-run and re-checked by anyone. |
| **Scale controls** | Filtering by test ID, name, group, tag or directory; scenario caching; containerised execution. | Large suites stay practical to run in CI and in the lab. |

## 4. AI in CPACT — today and next

This is the section to be precise about, because it is the easiest one to oversell.

### Today: AI assists the people around the tool

**CPACT ships no model.** There is no LLM call anywhere in the execution path. Scenario
execution, schema validation and scoring are fully deterministic — the same recipe
against the same target yields the same score, every time. That property is
non-negotiable: a compliance result that a model could nudge is not evidence.

Where AI helps today is in the human work that surrounds the tool:

- **Schema-guided recipe authoring.** The Draft-7 JSON Schema is a precise, machine-readable
  grammar for what a valid recipe looks like. Hand that schema to an AI assistant and it
  can draft, complete and correct scenario YAML against it — and the result is then
  *verified by the schema validator*, not trusted on faith. The assistant proposes; the
  deterministic validator decides. Recipe authoring goes from an expert-only task to
  something a domain engineer can do in an afternoon.
- **Review of recipe diffs and spec changes.** When the specification moves (0.7 → 0.8),
  an assistant can summarise what changed, which recipes are affected, and what a
  migration looks like — the kind of cross-cutting reading that is slow and error-prone
  by hand.
- **Log triage.** A failing run produces large CPACT and workload logs. AI-assisted
  reading shortens the path from "step 7 failed" to "here is the relevant 40 lines".

The honest framing: **AI accelerates authoring, review and triage. It does not produce
the compliance verdict.**

### Next: on the roadmap

Clearly labelled as *not yet built*:

- **Natural language → validated recipe.** Describe a compliance intent in prose; get a
  candidate recipe back, automatically checked against the schema before it is offered.
  The schema remains the gate.
- **AI log analysis with attribution.** Go past summarisation to naming the failing step
  and a likely root cause, grounded in the run's own artifacts.
- **Behavioural drift detection.** Compare runs across firmware revisions and flag
  behaviour that changed without a corresponding spec change — a regression class that
  pass/fail testing misses entirely.
- **Coverage advisor.** Analyse the suite against the specification and report what is
  *not* being exercised. "What did we forget to test" is the question that a deterministic
  suite structurally cannot answer about itself.

The design principle to state out loud when presenting: **AI on the edges, determinism in
the core.** Anything that touches the score stays reproducible and auditable.

## 5. How it changes the validation industry

- **Compliance as code.** The requirement and the proof become one version-controlled
  artifact, reviewed through normal code review. Specification drift — where the document
  and the tests slowly disagree — stops being possible, because they are the same thing.
- **Evidence replaces assertion.** Weighted, comparable scores across vendors and CPU
  generations mean procurement and architecture decisions rest on executed results rather
  than datasheet claims. A supplier can also *demonstrate improvement*, which turns
  compliance from a gate into an incentive.
- **Shift-left economics.** An accessibility gap found by the supplier at bring-up is a
  firmware fix. The same gap found by the operator at fleet scale is an incident, a
  qualification programme, and possibly stranded capacity. CPACT moves discovery to the
  cheap end.
- **Continuous gate, not an annual audit.** Because runs are repeatable and the output is
  machine-readable, accessibility becomes a CI check that runs on every firmware drop,
  instead of a point-in-time audit that is stale the moment it is signed.
- **A shared, open baseline.** Under OCP, suppliers and operators improve one suite
  together. Every scenario contributed raises the floor for the whole industry, and
  reduces the duplicated qualification effort that benefits nobody.

## Speaker talk track

A suggested path through the slide. The slide is dense by design — read the cards in
order and let the audience follow along rather than reading ahead.

1. **Open on the problem (card 1).** Lead with the concrete image: three suppliers, three
   completely different ways to pull a debug dump, and a document that claims all three
   are "accessible". Land the late-discovery failure mode — the gap is found mid-incident,
   at fleet scale.
2. **Why we built it (card 2).** Pivot from "this is painful" to "this is fixable": make
   the spec executable, scope it to the four domains that decide serviceability, and let
   suppliers self-certify. State the non-goals explicitly — it disarms the "is this a
   benchmark?" question before it is asked.
3. **What you gain (card 3).** Walk left to right. The single most persuasive line is
   *compliance as code* — recipes reviewed in a pull request like any other change.
   Mention the four connection paths as the "it tests the box the way the fleet reaches
   it" point.
4. **AI (card 4).** Be disciplined here. Say plainly that CPACT ships no model and that
   execution and scoring are deterministic — *then* explain that AI already changes the
   economics of authoring, review and triage because the schema gives a model exact
   grammar to work against. Mark the roadmap as roadmap. Technical audiences trust this
   framing far more than a vague "AI-powered" claim.
5. **Industry impact (card 5).** Close on shift-left economics and the continuous gate.
   The takeaway sentence: *accessibility stops being a document and becomes a test that
   runs on every firmware drop.*
6. **How to run it (card 6).** Only if the audience is hands-on. Otherwise skip it and use
   the time for questions.

### Anticipated questions

| Question | Answer |
| --- | --- |
| "Is this a benchmark?" | No. It measures whether accessibility interfaces exist and behave as specified, not how fast the part is. |
| "Does it replace our vendor diagnostics?" | No. It is a compliance layer on top; vendor diagnostics remain the deep-dive tool. |
| "Can the AI change our score?" | No. There is no model in the execution or scoring path. AI assists authoring, review and triage only. |
| "What happens when the spec changes?" | Recipes declare a `schema_version`; schemas are versioned side by side under `spec/schema/`. Recipes migrate deliberately, and validation catches the ones that have not. |
| "How do we compare two suppliers fairly?" | The same recipes, the same weights, the same connection paths. The score is normalised across schema, map and execution categories. |

## Content guardrails

If you edit the slide or this README, hold to these rules — they are what make the deck
safe to present externally:

1. **No invented numbers.** No adoption figures, no time-saved percentages, no benchmark
   results. Everything quantitative must trace to a repo file, as in the table above.
2. **No vendor or customer names.** CPACT is vendor-neutral, and the deck must read that
   way. "A supplier", not a brand.
3. **Roadmap stays labelled.** Anything not implemented appears under an explicit *Next*
   or *roadmap* heading. Never describe a planned AI capability in the present tense.
4. **Determinism claim is load-bearing.** Do not soften "CPACT ships no model" into
   "AI-powered compliance". The credibility of the whole AI section rests on that
   distinction.
5. **Keep it one slide.** The brief is a single slide. Depth belongs here in the README,
   not in extra slides.
